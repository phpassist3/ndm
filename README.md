# NDM — корректная передача X-Forwarded-For через цепочку nginx

Тестовый стенд на `docker-compose` из трёх nginx и небольшого приложения за ними.
Демонстрирует, как настроить обратные прокси так, чтобы:

1. Приложение получало в заголовке `X-Forwarded-For` **IP клиента и всех nginx**,
   через которые прошёл запрос — в порядке прохождения.
2. Заголовок `X-Forwarded-For`, **подделанный самим пользователем**, до приложения
   не доходил — первый nginx на пути его выкидывает.

---

## Топология

```
user ──► localhost:8081 ──► nginx1 ──► nginx2 ──► nginx3 ──► app
user ──► localhost:8082 ─────────────► nginx2 ──► nginx3 ──► app
user ──► localhost:8083 ─────────────────────────► nginx3 ──► app
```

Один и тот же образ nginx, одна и та же конфигурация — отличается только переменная
окружения `NEXT_HOP` у каждого инстанса.

Сеть `10.10.0.0/24`, контейнеры с фиксированными адресами:

| Контейнер | IP             | Опубликован |
|-----------|----------------|-------------|
| `app`     | `10.10.0.16`   | —           |
| `nginx3`  | `10.10.0.17`   | `:8083`     |
| `nginx2`  | `10.10.0.18`   | `:8082`     |
| `nginx1`  | `10.10.0.19`   | `:8081`     |

Доверенная подсеть для nginx — `10.10.0.16/28` (.16–.31). Шлюз docker-сети
`10.10.0.1` **сознательно** оставлен за пределами доверия: при обращении с хоста
через published-порт запрос приходит в контейнер с source IP шлюза, и если
бы шлюз считался доверенным, nginx принимал бы подделанный XFF от пользователя.

## Логика защиты XFF

Конфигурация одного хопа — [nginx/templates/default.conf.template](nginx/templates/default.conf.template).
Ключевая идея в трёх блоках:

```nginx
# 1. По адресу TCP-пира соврать нельзя — определяем "свой/чужой".
geo $is_trusted_proxy {
    default              0;
    10.10.0.16/28        1;
}

# 2. От внешнего клиента XFF выкидываем, от соседнего nginx — доверяем.
map $is_trusted_proxy $sanitized_xff {
    0   "";
    1   $http_x_forwarded_for;
}

# 3. Если цепочка пуста — стартуем её с реального IP клиента.
map $sanitized_xff $xff_with_client {
    ""      $remote_addr;
    default $sanitized_xff;
}

# В итоге к проксируемому запросу приклеиваем IP текущего nginx.
proxy_set_header X-Forwarded-For "$xff_with_client, $server_addr";
```

Каждый nginx добавляет **свой** IP (`$server_addr`) в конец цепочки —
приложение в результате видит полный путь, включая последний nginx перед собой.

## Запуск

Требования: Docker Desktop / Docker Engine с плагином `compose v2`.

```bash
docker compose up -d --build
```

Сборка занимает 10–20 секунд (один раз). Проверить, что всё поднялось:

```bash
docker compose ps
curl -s http://localhost:8081/healthz   # должно быть "ok"
```

Остановка и очистка:

```bash
docker compose down
```

## Протокол тестирования

Автоматический запуск всех сценариев:

```bash
bash tests/run-tests.sh
```

Скрипт ходит curl-ом по всем трём точкам входа, парсит JSON-ответ приложения и
проверяет `x_forwarded_for`. Зависимости: `curl`, `jq`.

Ниже — те же сценарии вручную, чтобы было видно, что именно проверяется.

### Сценарий 1. Цепочка длины 1: `user → nginx3 → app`

```bash
curl -s http://localhost:8083/ | jq .x_forwarded_for
```

Ожидается:

```
"10.10.0.1, 10.10.0.17"
```

`10.10.0.1` — это шлюз docker-сети, через который курл с хоста попадает в
контейнер (в реальном деплое здесь был бы публичный IP пользователя).
`10.10.0.17` — IP самого `nginx3`, который дописал себя в конец цепочки.

### Сценарий 2. Цепочка длины 2: `user → nginx2 → nginx3 → app`

```bash
curl -s http://localhost:8082/ | jq .x_forwarded_for
```

Ожидается:

```
"10.10.0.1, 10.10.0.18, 10.10.0.17"
```

### Сценарий 3. Цепочка длины 3 (полная): `user → nginx1 → nginx2 → nginx3 → app`

```bash
curl -s http://localhost:8081/ | jq .x_forwarded_for
```

Ожидается:

```
"10.10.0.1, 10.10.0.19, 10.10.0.18, 10.10.0.17"
```

Пользователь + все три nginx — в правильном порядке прохождения. Требование 1 выполнено.

### Сценарий 4. Защита от подделки на полной цепочке

```bash
curl -s -H 'X-Forwarded-For: 6.6.6.6' http://localhost:8081/ | jq .x_forwarded_for
```

Ожидается:

```
"10.10.0.1, 10.10.0.19, 10.10.0.18, 10.10.0.17"
```

`6.6.6.6` отсутствует — `nginx1` выкинул подделанный заголовок ещё на входе.
Цепочка построена честно: реальный IP клиента + IP всех nginx.

### Сценарий 5. Защита от подделки на короткой цепочке

```bash
curl -s -H 'X-Forwarded-For: 6.6.6.6' http://localhost:8083/ | jq .x_forwarded_for
```

Ожидается:

```
"10.10.0.1, 10.10.0.17"
```

Подделка выкинута даже когда между пользователем и приложением только один nginx.

### Сценарий 6. Множественная подделка (несколько XFF заголовков)

```bash
curl -s \
  -H 'X-Forwarded-For: 1.1.1.1' \
  -H 'X-Forwarded-For: 2.2.2.2, 3.3.3.3' \
  http://localhost:8081/ | jq .x_forwarded_for
```

Ожидается:

```
"10.10.0.1, 10.10.0.19, 10.10.0.18, 10.10.0.17"
```

Все три подделанных значения отброшены вне зависимости от того, как клиент
их прислал — одним заголовком или несколькими. Требование 2 выполнено.

### Сценарий 7. Попытка выдать себя за внутренний nginx

```bash
curl -s -H "X-Forwarded-For: 10.10.0.19" http://localhost:8082/ | jq .x_forwarded_for
```

Ожидается:

```
"10.10.0.1, 10.10.0.18, 10.10.0.17"
```

Даже если пользователь специально подставляет IP, похожий на внутренний nginx,
санитизация работает на уровне TCP-пира, а не содержимого заголовка — подмена
бесполезна.

## Что внутри логов nginx

`docker compose logs -f nginx1 nginx2 nginx3` показывает кастомный формат `chain`:

```
ndm-nginx1  | [nginx1] time=2026-05-21T13:30:00+00:00 tcp_peer=10.10.0.1 trusted=0 xff_in="6.6.6.6" xff_out="10.10.0.1, 10.10.0.19" method=GET uri=/ status=200
ndm-nginx2  | [nginx2] time=2026-05-21T13:30:00+00:00 tcp_peer=10.10.0.19 trusted=1 xff_in="10.10.0.1, 10.10.0.19" xff_out="10.10.0.1, 10.10.0.19, 10.10.0.18" method=GET uri=/ status=200
ndm-nginx3  | [nginx3] time=2026-05-21T13:30:00+00:00 tcp_peer=10.10.0.18 trusted=1 xff_in="10.10.0.1, 10.10.0.19, 10.10.0.18" xff_out="10.10.0.1, 10.10.0.19, 10.10.0.18, 10.10.0.17" method=GET uri=/ status=200
```

Видно, как:
- `nginx1` пометил клиента как `trusted=0`, входящий `6.6.6.6` отброшен.
- `nginx2` и `nginx3` пометили предыдущий nginx как `trusted=1` и продолжили цепочку.

## Замечания по решению

- В этом стенде IP «пользователя» в `X-Forwarded-For` отображается как `10.10.0.1` —
  это шлюз docker-bridge, через который локальный `curl` попадает в контейнер.
  В продакшене на его месте стоял бы публичный IP клиента, всё остальное —
  то же самое.
- Используется CIDR-подсеть `/28` (16 адресов) внутри `/24`: контейнеры в
  одной половине, шлюз — в другой. Это позволяет nginx-у однозначно различать
  внутренний трафик и пользовательский, не полагаясь на содержимое заголовков.
- В реальном деплое имеет смысл расширить ту же защитную логику на `X-Real-IP`,
  `Forwarded` (RFC 7239) и любые другие заголовки, по которым приложение
  определяет источник запроса — принцип идентичен.
- Образ nginx залочен на минорной версии (`1.27-alpine`) — воспроизводимая сборка.
  При желании можно перейти на digest pinning.
